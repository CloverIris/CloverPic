# CloverPic 主窗口性能复盘（2026-10-22）

这份文档记录一次真实采样：程序运行、人工操作、关闭，全程 `sample` 每 2ms 采样一次。
所有数字都来自本机实测，不是估算。

## 1. 结论先行

| 指标 | 数值 |
|---|---|
| 工作区单帧渲染（Release，3008×1758 = 5.3M 像素） | **42.2 ms** → 23.7 fps 上限 |
| 工作区单帧渲染（Debug，-O0，同样的像素） | **318.1 ms** → 3.1 fps |
| Program Manager 单帧（1634×1226，Release） | 9.7 ms |
| 主线程采样中落在整帧 `Render` 的比例（操作期间） | **39%** |
| 上述时间里花在纯像素搬运（Clear/棋盘/Blit/渐变）的比例 | **86%** |

同一分辨率下，CloverPlatform 的对照数据：

| 场景 | 耗时 |
|---|---|
| 整帧重绘（3000×1700） | 11.7 ms |
| **一次交互引起的最小重绘** | **0.160 ms** |

一次交互的重绘成本，两者相差 **264 倍**（42.2 / 0.16）。

## 2. 采样里看到的事实

操作期间的主线程（1627 个采样点，约 3.25 秒）：

```text
NSApplication run                                   985
├─ 运行循环观察者 → CATransaction → 图层显示 → drawRect   711
│    └─ WorkspaceRuntime::Render                        637
│         ├─ SoftRenderer::Clear（整帧）                  200
│         ├─ DrawCheckerboard（整块画布）                 129
│         ├─ BlitBgra（合成层拷贝）                       121
│         ├─ FillVerticalGradient（面板渐变）               96
│         └─ 其余：面板装饰、文字、描边                       91
├─ mach_msg 等待（空闲）                                   216
└─ 事件处理（用户点击关闭按钮 → 未保存确认）                  642
```

三个事实：

1. **`WorkspaceRuntime::Render` 无条件重画整帧。** 代码里 `ConsumeDirtyRects()` 的返回值被丢弃，
   `outDirtyRects` 直接填 `FullRect()`。
2. **每一帧都要三次全表面遍历**：`Clear` 整帧 → 画棋盘 → 把画布层 `BlitBgra` 合成回去。
   这三项加起来是渲染时间的 71%。
3. **每次鼠标移动都会触发一次重绘。** 适配层 `sendPointer` 无条件 `setNeedsDisplay`，
   而一次重绘要 42ms——鼠标事件 16ms 来一个，队列必然堆积。

## 3. 根因（按贡献排序）

1. **`-O0` 的 Debug 构建**（7.5 倍）。`CMAKE_CXX_FLAGS_DEBUG=-g` 没有 `-O`，
   而这个项目的主渲染路径是 CPU 逐像素循环。
2. **整帧重绘**：脏矩形算出来了但不用。
3. **每次输入都全帧重绘**，没有合并、没有节流、没有帧预算。
4. **三次冗余全表面遍历**：clear / 棋盘 / blit 各自都是一遍 5.3M 像素。
5. **画布合成无脏标记**：即使画布没变，也每帧重新合成。

## 4. 教训

### 4.1 构建配置是性能的一部分
Debug 构建是 3 fps，Release 是 24 fps。同一份代码，7.5 倍差距。
把 Debug 的二进制定性为"卡"，会误导所有后续优化。

### 4.2 「算出了脏矩形」不等于「用了脏矩形」
`FrameScheduler` 认真积累了脏区，`Render` 却把结果丢掉。这种"算而不用"比完全没有更危险：
它让人以为已经优化过。

### 4.3 一次纠正不了结构，就每次都要付钱
全帧 `Clear` + 全帧棋盘 + 全帧 blit 是**逐帧重复的三份工作**，而屏幕上 99% 的像素没有变化。
每帧一次的全表面遍历，是"没有抽象 UI"的直接后果：没有场景树，就没有"只有这一块变了"的概念。

### 4.4 输入频率远高于渲染能力时，系统不会自愈
鼠标 60–120 次/秒，渲染 24 次/秒。没有合并与丢帧策略，延迟只会越积越多。
**必须有帧预算和合并**，而不是"来一个事件画一次"。

### 4.5 框架自己也会犯同一个错
CloverPlatform 最初 `UiTree::layout()` 每次调用都标记整个根节点脏——结果 `hover` 重绘
12.03ms ≈ 整帧 11.7ms，损伤重绘完全失效。加一个 `layout_dirty` 门控后降到 **0.160ms**。
这说明：**损伤追踪不是一个功能，而是一条纪律**，任何一个环节破例标脏就会全线失效。

## 5. CloverPlatform 的组织架构原则

以下几条是从上面这些数字里倒推出来的，建议写进框架的约束里。

### P1. 按职责切层，不按技术切层
`clover-core` 只有数据与几何；`clover-ui` 只有树/布局/输入语义；`clover-render` 只有像素；
`clover-abi` 只有边界。跨层调用只允许向下。这条已经在执行，效果是整个渲染层可以整体替换（GPU）。

### P2. 状态各有唯一所有者
damage 只能有一个拥有者（现在是 `UiTree`）。曾经 `UiTree` 和 `Surface` 各存一份，
导致输入引起的重绘被静默丢弃，单元测试还是绿的——因为测试断言的是状态不是像素。

### P3. 一切"每帧执行"的步骤都必须有门控
layout、display list 构建、像素绘制，三者都要能被跳过。
判定条件必须是显式的 dirty 标志，不能靠"顺手标脏"。

### P4. 性能是可测量的契约，不是感觉
每个 crate 都应有基准（现在 `bench_workspace`、`bench_clover` 都是可重跑的独立程序）。
合入前看数字，不看"感觉快了"。

### P5. 平台适配层不做像素决策
适配层只负责：开窗、翻译输入、把 core 输出的 frame 贴上去。
分辨率、缩放、重绘范围由框架/core 决定。macOS adapter 现在做的事正好只有这些。

### P6. 输入与渲染解耦
输入只改状态并标脏；渲染由节拍驱动，带合并与预算。
一个输入事件永远不应该同步触发一次渲染。

## 6. CloverPic Core UI 重写的建议路径

目标：把 `src/Core/UI` 那套手写 scene + `SoftRenderer` 换成 `.cui` + CloverPlatform，
Core 只保留模型、命令、文档。

**阶段 0：先做基线（半天）**
- macOS 默认构建改成 Release；加一个可开关的帧时间/分块数覆盖层。
- 不改任何 UI 代码，先拿到"改造前"的确定性数字。

**阶段 1：工作区外壳搬到 .cui（1–2 天）**
- 顶部菜单栏、工具栏、左右 dock、状态栏 → 一个 `.cui` 文档。
- 画布区域留成 `<CloverSurface>` 直接内存区。
- 面板拖拽/resize 用框架的布局 + 动作实现，不再由 core 自己算矩形。

**阶段 2：画布走零拷贝（1 天）**
- 现在 core 每帧把 RGBA10 瓦片合成到 BGRA 再整块 blit。
- 改为：画布线程直接写 `DirectSurface`，框架合成时采样。
- 预期：把 121 + 129 + 200 = 450 个采样点（约 71% 的渲染时间）削掉大半。

**阶段 3：拆掉 SoftwareRenderer 的 UI 部分**
- `WorkspaceNodeRenderer`、`ProjectManagerRenderer`、`IconPainter` 逐步删除。
- `SoftRenderer` 只保留画布合成需要的最小部分，或整体交给框架。

**阶段 4：验证**
- 像素对照：同一份项目数据，新旧两版截图差异在阈值内。
- 输入回放：录一段鼠标/键盘事件序列，两版行为一致。
- 性能预算：整帧 < 8ms，交互重绘 < 1ms（4K 分辨率下）。

## 7. 需要立刻改的（不等重写）

1. `WorkspaceRuntime::Render` 用 `ConsumeDirtyRects()` 的返回值提供 `outDirtyRects`，
   适配层按脏区贴图（Windows 的 per-rect blit 已经有实现，macOS 需要补）。
2. 适配层对 `PointerMove` 做合并：一帧内多次移动只标一次脏。
3. macOS 构建默认 Release。
